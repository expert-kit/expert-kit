# NPU 纯通信后端对照（2026-09-26）

结论：本版 Ascend Direct 大包通信显著加快；8A 并发下的 8 KiB 小包仍比 gRPC 慢。通信层自身已经可以复现回退。

## 方法

在 `.85` 的真实 NPU 上直接调用既有 WorkerTransport 和 Receiver，E 原样回传收到的激活。没有加载模型，没有调用 vLLM、Controller、路由框架或专家计算后端。

计时从 A 调用 `execute` 到返回数据在 A 的 NPU 上可用，包含通信后端的 staging、编解码、校验、控制消息、线程调度、数据传输和同步。双方使用相同的 echo 消费循环与结束条件；这是通信后端的完整往返延迟。

- 代码实现 `55185b8`，测试 checkout `b5c54f0`，后者只增加文档。
- A NPU 0–7，E NPU 8–15；两端 Torch / torch-npu 2.11 / CANN 9.0.1，同一镜像 `ek-npu-transport-dev:ascend1`。
- BF16，hidden_dim 4096，top_k 6；路由字段作为通信协议元数据传输，不做专家选择或计算。
- 每个 peer 一个在途请求，A 原生执行器 2 线程；gRPC 每个 peer 使用自己的执行器。
- 每组预热 20 次，每个 A 采样 100 次；连接、注册内存和缓冲在采样前建立并复用。
- 预热后及采样后检查回传数据精确相等；正式 8A 运行给每个 A 不同的激活内容。

## 解读与下一步

单 peer Ascend RTT 从 8 KiB 到 4 MiB 大致维持 2.6 ms，而 gRPC 从 1.9 ms 增至 14.1 ms。这支持大块数据在本版直传路径中的收益；小包的完整后端固定成本仍较高，多 A 竞争下也存在回退。

现有真实模型阶段计时中，原生 READ / WRITE 本体合计约 0.60 ms，其 await 接口合计约 1.33 ms；差值包含线程排队、设备上下文、提交与唤醒，不能全部称为队列等待。E 输入还会把路由元数据拷回 CPU 并同步，A/E 接收后使用设备屏障，控制面仍是 gRPC 流。这些已确认的通信代码路径是下一步逐项做单变量优化的对象，当前测试尚未隔离各项因果贡献。

后续聚焦通信后端：合并任务与完成通知、减少小包控制和调度开销、优化路由元数据传输及同步粒度，并沿用这套纯通信回环检查收益和内容。

## 生命周期观察

单 A 测量全部完成后，显式 `CloseSession` 的注销阶段报 `Mooncake memory deregistration failed with native status -1`。原始日志与状态已保留，A exit 1，E 经停止后 exit 137，均非 OOM。这个错误发生在采样和内容检查之后。

正式 8A 数据测试在所有响应及目标 NPU 流完成后退出客户端进程，再停止 E，使用全新的进程进行两后端比较，所有专用进程最后退出且 NPU 无运行任务。该清理策略不验证运行中关闭/注销/同 endpoint 重连；生命周期问题仍需修复，数据路径性能不代表生产部署的稳定性已全部验证。
